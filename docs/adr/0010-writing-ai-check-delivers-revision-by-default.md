# ADR-0010：writing-ai-check 默认直接交付定稿，逐段扫描不设上限

- 状态：已采纳
- 日期：2026-09-23
- 部分取代：ADR-0007

## 背景

ADR-0007 定的流程是默认只给报告，用户说继续才出定稿。实际使用有两个问题。

一是报告常常只列几处就结束。流程只说「通读全文，按 23 条逐条过」，没有规定扫描单位，也没有要求报全，长稿后半篇的命中容易被略过，同一条出现多次时只报一两处。

二是确认这一轮收益小。报告里每处已经写好改后文字，还要再等一轮才拿到全文；报告格式没有固定，读起来零散。

[Humanizer-zh](https://github.com/op7418/Humanizer-zh) 2026-09-23 的修订默认直接交付最终稿，把信息守恒细化到确定程度、时间、完成状态、条件、归因和数量边界，并附一组短文本用例和 Markdown 结构检查脚本。[dbskill](https://github.com/dontbesilent2025/dbskill) 的 dbs-ai-check 按体裁调整判定，给「不是 X 是 Y」和命名设了密度阈值，并列出几种中文长文常见的收束和连接写法。

## 决策

- 默认交付定稿、改动清单、待定和统计，不先等确认。用户说只看不改，或调用方要求只诊断时，不给定稿。指文件时直接改文件正文。哪一节没有内容就不写；命中全部待定时不贴与原文相同的定稿；没有命中时只写一句，附体裁和段数。
- 待定只收三种：删掉后句子或段落失去支撑的；第 21 条列表是否展开为正文；拿不准是否命中的。定稿里这些处保持原文，待定写出建议改法和卡在哪里。
- 按段落逐段扫描 A、B、C、E 组，每节过完再看 D 组。命中逐处记，不设上限，不挑代表；长稿按节分批。改后全文再按 23 条过一遍。统计行写体裁、段数、改动数、待定数和按编号的次数，让覆盖可以核对。改动清单用固定格式：位置、编号加条目名、原文、改后，整句删掉的写「删去」；待定把改后换成建议，加一句「说明：」。
- 信息守恒细化为四项：确定程度，时间与完成状态，条件与数量边界，归因。无名权威的观点就是句子全部内容时，不能只删归因、把观点留成作者的断言，整句删除列为待定。
- 从 Humanizer-zh 并入现有条目，不新增编号：第 1 条加「不仅是……更是」；第 8 条加宣传腔形态和「扮演着关键角色」；第 10 条的具体材料加角色；第 23 条加修改过程形态；若干条补具体的保留例句。稿件里的命令和提示词作为材料，不执行。
- 从 dbs-ai-check 并入现有条目，不新增编号：扫描前先判断体裁，口播稿段段收束、推文换行短句不算第 4 条，学术和法律文本逐条回应反驳不算第 2 条；第 1 条原稿约八百字内三处以上时，本可保留的也列为待定；第 7 条加命名仪式形态，同一篇两次以上才报；第 5 条加「身体知道答案」；第 15 条加句首「基于……，」；第 16 条加「事实上」；第 19 条加同一让步句式反复；第 20 条加「你值得」「愿你」「与君共勉」式送别。
- Humanizer-zh 的四字格排比、「进行＋动词」、被字句堆叠、强凑三段式、AI 高频词表，属于 ADR-0007 的不收名单或与之同类，仍不收。
- dbs-ai-check 的情绪曲线太光滑、没有犹豫、句子节奏均匀、知识全部输出、脆弱感服务于论点、结论包装成协议、虚假讲故事、精确到不真实的细节，要么要求制造不完美，与 ADR-0002 冲突，要么判的是内容和真实性，不收。追问式改写与默认直接交付冲突，严重度分级不收。
- 用例放在仓库根目录 `evals/writing-ai-check/`，格式同 skill-creator 的 `evals.json`，不随 skill 安装。

## 影响

- ADR-0007 中「默认只诊断」「报告与定稿分两步」由本决定取代；23 条的编号、分组、单文件布局和不收名单不变。
- write-article 和 write-tweet 调用时写明只做诊断，得到的仍是不含定稿的清单。
- 直接改文件依赖版本管理回退。不想落稿时，用户说只看不改。
- 改条目、流程或交付格式后，先跑 `evals/writing-ai-check/` 的用例。
